Casos de uso a detalle   
F1 Gestionar Clientes   
F1.1 Crear Cliente  
  
Descripción  
Este caso de uso permite al administrador ingresar los datos de un nuevo 
cliente en el sistema. El sistema valida que la información sea correcta y 
que el cliente no exista previamente, para luego almacenarlo y dejarlo 
disponible para los procesos de facturación.  
• Actor: Administrador  
Flujo principal:  
1. El administrador selecciona la opción Crear Cliente  desde el módulo de 
Gestión de Clientes. 


2. El sistema despliega el formulario de registro con los campos: identificación, 
nombres, apellidos, dirección, teléfono y correo electrónico. 
3. El administrador ingresa la información del cliente y confirma la operación. 
4. El sistema verifica que todos los campos obligatorios estén completos y que 
el número de identificación no exista previamente en la base de datos. 
5. El sistema almacena la información del cliente en la base de datos del sistema 
de facturación. 
6. El sistema muestra un mensaje de confirmación indicando que el cliente fue 
registrado correctamente. 
Flujos alternos:  
A1: Datos no válidos → el sistema muestra mensaje y solicita corrección.  
A2: Cliente duplicado (identificación/correo) → el sistema notifica y no 
registra.  
 
F1.2 Modificar Cliente  
  
Descripción  
Este caso de uso permite al administrador modificar los datos de un 
cliente existente, garantizando que la información se mantenga 
actualizada y refleje correctamente los cambios realizados. •   
Actor: Administrador  
Flujo principal:  
1. El administrador selecciona un cliente registrado desde la lista de clientes 
del sistema. 
2. El administrador selecciona la opción Modificar Cliente. 
3. El sistema carga y muestra los datos actuales del cliente en el formulario 
de edición. 
4. El administrador actualiza uno o más campos del cliente. 


5. El sistema valida que los datos modificados cumplan con las reglas 
definidas y que no exista duplicidad de identificación. 
6. El sistema guarda los cambios en la base de datos del sistema de 
facturación. 
7. El sistema muestra un mensaje de confirmación indicando que el cliente 
fue actualizado correctamente. 
Flujos alternos:  
A2: Cliente no encontrado → sistema informa y regresa al listado.  
F1.3 Eliminar Cliente  
  
Descripción  
Este caso de uso permite al administrador retirar un cliente del sistema, 
evitando que siga siendo utilizado en los procesos de facturación, 
manteniendo la base de datos organizada.  
Actor: Administrador  
Flujo principal:  
1. El administrador selecciona un cliente registrado desde la lista de clientes del 
sistema. 
2. El administrador selecciona la opción Eliminar Cliente. 
3. El sistema muestra un mensaje de confirmación solicitando autorización para 
eliminar el cliente seleccionado. 
4. El administrador confirma la eliminación del cliente. 
5. El sistema elimina o marca como inactivo el registro del cliente en la base de 
datos del sistema de facturación, según la política definida. 
6. El sistema muestra un mensaje de confirmación indicando que la operación se 
realizó correctamente. 
Flujos alternos:  
1. A1: Cancelar confirmación → no se realizan cambios.  


2. A2: Cliente con registros asociados → el sistema 
bloquea eliminación y notifica al administrador. 
F1.4.1 Consulta General   
  
Descripción  
Este caso de uso permite al administrador consultar de manera general 
todos los clientes existentes, facilitando la revisión y control de la 
información almacenada.  
• Actor: Administrador  
Flujo principal:  
1. El administrador selecciona la opción Consulta General dentro del módulo 
Consultar Cliente. 
2. El sistema recupera todos los clientes registrados desde la base de datos del 
sistema de facturación. 
3. El sistema muestra en pantalla el listado completo de clientes con su 
información principal. 
F1.4.2 Consulta por Parámetro 
  
Descripción  
Este caso de uso permite al administrador filtrar clientes utilizando 
parámetros como nombre, identificación o correo, mostrando únicamente 
los registros que coincidan con la búsqueda.  
• Actor: Administrador  
Flujo principal:  
1. El administrador selecciona la opción Consulta por Parámetro dentro del 
módulo Consultar Cliente. 


2. El sistema muestra los campos disponibles para filtrar la búsqueda 
(identificación, nombre, correo u otros criterios definidos). 
3. El administrador ingresa uno o más parámetros de búsqueda y confirma la 
consulta. 
4. El sistema valida los parámetros ingresados. 
5. El sistema consulta la base de datos utilizando los parámetros definidos. 
6. El sistema muestra en pantalla los clientes que cumplen con los criterios de 
búsqueda. 
Flujos alternos:  
A1: Sin coincidencias → muestra “0 resultados”.

F4 — Gestión de Compras 
F4.1 Registrar Compra 


  
Descripción 
Este caso de uso permite al administrador registrar una compra en el sistema, 
asociándola a un proveedor y a los productos adquiridos, con el fin de actualizar el 
inventario y mantener un control adecuado de las operaciones de compra. 
Actor 
Administrador 
Flujo principal 
1. El administrador accede al módulo Gestión de Compras y selecciona la opción 
Registrar Compra. 
2. El sistema muestra el formulario de regi stro de compra con los campos: 
proveedor, fecha de compra, número de comprobante, tipo de comprobante y 
detalle de productos. 
3. El administrador selecciona un proveedor registrado en el sistema. 
4. El administrador agrega uno o más productos a la compra, ingresando la cantidad 
y el costo unitario de cada producto. 
5. El sistema calcula automáticamente el subtotal, impuestos y total de la compra. 
6. El administrador confirma el registro de la compra. 
7. El sistema valida que el número de comprobante no esté duplicado y que los datos 
ingresados sean correctos. 
8. El sistema registra la compra en la base de datos del sistema de facturación. 
9. El sistema actualiza automáticamente el stock de los productos adquiridos en la 
bodega. 
10. El sistema muestra un mensaje de confirmación indic ando que la compra fue 
registrada correctamente. 
Flujos alternos 
A1. Datos no válidos 
El sistema muestra un mensaje indicando los campos incorrectos o incompletos y 
solicita al administrador corregir la información ingresada. 
A2. Comprobante duplicado 
El sistema notifica que el número de comprobante ya existe y no permite registrar la 
compra. 


F4.2 Modificar Compra 
  
Descripción 
Este caso de uso permite al administrador actualizar la información de una compra 
registrada en el sistema (datos del comprobante y/o detalle de productos), 
manteniendo la consistencia de los registros y del inventario. 
Actor 
Administrador 
Flujo principal 
1. El administrador accede al módulo Gestión de Compras y visualiza el listado 
de compras registradas. 
2. El administrador selecciona una compra existente y selecciona la opción 
Modificar Compra. 
3. El sistema muestra el formulario con los datos actuales de la compra (proveedor, 
fecha, comprobante y detalle de productos). 
4. El administrador edita uno o más campos permitidos de la compra y/o modifica 
el detalle de productos (agregar, quitar o actualizar cantidades/costo unitario). 
5. El sistema recalcula automáticamente el subtotal, impuestos y total de la compra 
según los cambios realizados. 
6. El administrador confirma la actualización de la compra. 
7. El sistema valida que los datos ingresados sean correctos y que el número de 
comprobante no genere duplicidad (si fue modificado). 
8. El sistema guarda los cambios de la compra en la base de datos del sistema de 
facturación. 
9. El sistema actualiza el stock de los productos en bodega según las diferencias 
entre el detalle anterior y el nuevo detalle. 
10. El sistema muestra un mensaje de confirmación indicando que la compra fue 
actualizada correctamente. 
Flujos alternos 


A1. Datos no válidos 
El sistema muestra un mensaje indicando los campos incorrectos o incompletos y 
solicita corrección.

Descripción

DISEÑO 
Esta fase tiene como propósito definir cómo se construirá el sistema, estableciendo su 
arquitectura y especificando la interacción entre sus componentes. Durante esta etapa, se 
elabora un diseño de alto nivel, se crean prototipos de interfaces, se fijan estánda res de 
desarrollo y se planifica la integración del sistema. 
Es crucial porque proporciona una estructura clara para la implementación, facilitando la 
organización del código, reduciendo errores y asegurando la coherencia del desarrollo. 
 
Arquitectura de 3 Capas 
La arquitectura de 3 capas es un modelo ampliamente utilizado en el desarrollo de 
aplicaciones para separar las responsabilidades del sistema en tres niveles principales. 
Esto mejora la organización, el mantenimiento y la escalabilidad del software. 
GUI: Interfaz Gráfica de Usuario 
• Es la capa más cercana al usuario. 
• Responsable de la interacción con el usuario final, capturando entradas y 
mostrando salidas. 
• Consiste en ventanas, botones, formularios, y otros elementos gráficos. 
• Comunica las solicitudes del usuario a la capa DP y muestra los resultados 
procesados. 
DP: Dominio del Problema  
• Contiene la lógica del negocio y las reglas para procesar los datos. 
• Define cómo los datos se transforman o procesan según los requerimientos del 
negocio. 
• Actúa como un intermediario entre la GUI y la MD, asegurándose de que las 
operaciones cumplan con las reglas definidas. 
MD: Manejo de Datos 
• Responsable de todas las operaciones relacionadas con la base de datos. 

• Contiene las consultas SQL para crear, leer, actualizar y eliminar datos (CRUD). 
• Está directamente vinculada a las tablas y registros de la base de datos
